01 / 问题

并行交付里，最贵的不是写代码，
是找回上下文。

A

提交信息散落

分支、commit、平台编号、得分和截图链接分散在聊天与报告里。回填时才发现少了一项。

B

状态靠记忆

哪个任务阻塞、哪个已经可交，没有一张全局视图。风险任务不会自己浮到最上面。

C

交接要重读

换一个 Agent 或隔一天回来，要从头翻对话才能知道做到哪、下一步是什么。

“代码推了，但没提交；提交了，但证据找不到。” —— 看板要消灭的状态

02 / 工作流

一块看板，三次接力。

从“做了什么”到“下一步做什么”，信息不再停留在某一次对话里。

  1. 01

    记录任务与证据

    每张卡片承载仓库、分支、commit、提交编号、得分与证据链接。阻塞和待提交自动排在前面。

    SQLite · 结构化字段
  2. 02

    状态变更即写入记忆

    切换状态、补证据或回填提交信息时，向 PowerContext 写入一条带任务与时间的进展。

    PowerContext · memory/remember
  3. 03

    下次打开自动恢复

    偏好初始化标题与筛选，最近的进展回到时间线。接手者从当前进度继续，而不是从零开始。

    Bootstrap · 偏好 + 进展

03 / 能力

为交付收尾而设计。

风险优先

阻塞、待提交、进行中、待开始、已提交、已评分，按需要处理的顺序排列。

提交字段齐全

仓库、分支、commit、提交网址、平台任务编号、得分和证据链接，一个任务一次填全。

多维筛选

按方向、难度、状态过滤，按任务、仓库和下一步搜索，视图始终围绕当前关注点。

偏好复用

看板标题、默认方向与状态保存到 PowerContext，下次打开自动回到上次的视图。

进展时间线

每次状态变更留下任务、状态、下一步和时间，右侧即可看到最近的交接轨迹。

可复现验证

种子数据、接口验证、重启恢复和浏览器交互都有脚本与证据文件，评审核对成本低。

04 / 技术结合

记忆不是装饰，
它在核心链路上。

项目选用 PowerContext 1.2.0 的基础记忆能力：显式写入、FTS 检索，不需要模型 API。 应用启动时自动拉起受管理的真实服务，不依赖预先运行的 127.0.0.1:18801； 偏好与进展各走同一条读写链路，验证脚本可以按 run_id 精确命中。

  1. 读取/api/bootstrap 合并最新偏好到标题与筛选，并返回进展时间线。
  2. 写入PATCH /api/tasks/{id} 或保存偏好时，调用 memory/remember。
  3. 证明/api/memory/search 命中 run_id；服务重启后同一 Scope 仍可读取。
请求
POST /v1/memory/remember
{
  "scope_id": "scp_…",
  "kind": "progress",
  "text": "[progress] {\"task\":\"DS-06\",
           \"status\":\"doing\",

07 / 运行

一条命令，启动全栈。

依赖安装在本地，应用自动拉起真实 PowerContext（SQLite），无需另开终端、数据库服务或 API Key。

  1. 01创建虚拟环境并安装依赖
  2. 02启动看板：python -m board
  3. 03首次启动自动拉起 PowerContext 并播种任务、偏好与进展
  4. 04打开 127.0.0.1:18800
完整运行说明 源码目录

Windows 命令如下；Linux / macOS 将 .venv\Scripts\ 替换为 .venv/bin/。单命令启动，退出时应用会停止受管理的 PowerContext。

quickstart · qoder/ 
cd qoder
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt

# 单命令：自动启动看板 + 受管理的 PowerContext
.venv\Scripts\python -m board

# 打开 http://127.0.0.1:18800
